## P1 — Cancel target effect uses remaining open quantity (R11 patch)

**Context:** v1.10 used `target.quantity` (full order quantity) when computing the
counterfactual position after cancel. That overstates the cancel's impact when the
target is partially filled — a half-filled buy that gets canceled removes only the
unfilled half from future exposure, not the whole order.

**Patch:** For `source_type='cancel'`, the predicate computes against remaining open
quantity:

```
-- Inside the cancel branch of is_genuinely_risk_reducing(...)

target_remaining_qty       := target.quantity - target.filled_quantity
target_signed_remaining_qty:= CASE target.side
                                WHEN 'buy'  THEN +target_remaining_qty
                                WHEN 'sell' THEN -target_remaining_qty
                              END
Q_if_target_remaining_filled := Q + target_signed_remaining_qty

target_was_reducing := (abs(Q_if_target_remaining_filled) < abs(Q))
                       AND (sign(Q_if_target_remaining_filled) = sign(Q)
                            OR Q_if_target_remaining_filled = 0)

is_genuinely_risk_reducing := NOT target_was_reducing
```

Where `Q` is current signed position quantity (from the latest `position_snapshots`
row consistent with the evaluation's `as_of_at`/`fill_cutoff_at`).

**Note on V1 alternate:** if `trading.orders.canceled_quantity` exists, the first
line becomes:

```
target_remaining_qty := target.quantity
                      - target.filled_quantity
                      - target.canceled_quantity
```

This is a one-line change. The rest of the predicate is unaffected.

**Audit symmetry (per R10 holistic principle):**

- Drawdown: drawdown evaluates NAV state, which cancels do not mutate. Cancel branch
  of drawdown evaluation uses current NAV, blocking gated by the predicate as-is. No
  formula change. ✓
- Instrument-limits: see P3.
- CB block_new_risk: predicate is the gate; updated formula propagates. No additional
  change needed. ✓
- result_reason taxonomy: see P4.

## P2 — Cancel-no-effect handling (R11 sub-Q1, Option C)

**Context:** When `target_remaining_qty = 0` (target order is already fully filled or
fully canceled by the time the cancel evaluation runs), R11's formula naturally yields
`target_was_reducing = false` (since `Q_if_target_remaining_filled = Q`, abs equality
not strict less-than) and therefore `is_genuinely_risk_reducing = true`. This is
semantically wrong — a no-op cancel should not be classified as risk-reducing,
because it doesn't reduce anything.

**Patch (Option C, per reviewer lean):** Special-case zero remaining ahead of the
predicate body:

```
IF target_remaining_qty = 0 THEN
    is_genuinely_risk_reducing := false
    result_reason              := 'evaluated:cancel_no_effect'
    blocking                   := false   -- no state change to block
    -- exception: CB hard_stop still applies (see P7)
END IF
```

**Effects:**
- `is_genuinely_risk_reducing = false`: no-op cancels do not bypass blocking limits
  (audit-correct; no-op shouldn't be a risk-reduction escape hatch).
- `blocking = false`: nothing happens regardless of limit state, so blocking is
  pointless. The exception is CB `hard_stop`, which by definition blocks all
  evaluations regardless of predicate (preserves fail-closed semantics).
- New `result_reason` value: `evaluated:cancel_no_effect`.

**Why not Option A or B (assumed reviewer summary):**
- Option A (skip evaluation entirely): loses the audit row. v1.10's R7 patch
  ("one row per applicable limit always") is a hard invariant; we must record the
  evaluation.
- Option B (predicate=true, blocking=false): semantically misleading. A reviewer
  scanning rows for "did anything reduce risk?" would see the no-op as risk-reducing.
  Pollutes the audit signal.
- Option C: predicate=false, blocking=false, distinct result_reason. Clean.

**Audit symmetry:**
- Drawdown: a no-op cancel against drawdown is a no-op cancel; same special-case
  applies. drawdown evaluation row gets `result_reason='evaluated:cancel_no_effect'`,
  blocking=false. ✓
- Instrument-limits: same. See P3.
- CB block_new_risk: hard_stop still blocks; block_new_risk falls through to
  predicate=false → blocking still false (no state change). ✓
- result_reason: new value `evaluated:cancel_no_effect`.

## P3 — Instrument-scope limits for cancel: explicit semantics (R11 sub-Q2)

**Context:** v1.10 left implicit the question of which exposure value
instrument-scope limits should evaluate against for cancels. The reviewer correctly
flagged that this needs explicit design.

**Patch (verbatim incorporation of R11 sub-Q2 with elaboration):**

For `source_type='cancel'`, instrument-scope limits (max_position_quantity,
max_notional_usd at instrument scope) evaluate against **current exposure Q**, not
a counterfactual Q' that includes the cancel's effect. Rationale: cancel does not
itself change current position. The post-cancel position is identical to the
pre-cancel position; only the *future* exposure (if the canceled order had filled)
changes.

```
-- Inside risk.evaluate_action, instrument-limits branch, for source_type='cancel':

evaluated_exposure := Q                              -- not Q', not Q_after_cancel
limit_breached    := evaluated_exposure exceeds limit_value
blocking          := CASE
                       WHEN NOT limit_breached            THEN false
                       WHEN is_genuinely_risk_reducing    THEN false  -- escape hatch
                       ELSE limit_definition.blocking
                     END
result_reason     := CASE
                       WHEN NOT limit_breached            THEN 'evaluated:within_limits'
                       WHEN is_genuinely_risk_reducing    THEN 'evaluated:reducing_exit'
                       ELSE 'evaluated:limit_breached'
                     END
```

**Note:** A breaching cancel against an instrument-limit can only be
`is_genuinely_risk_reducing=true` if the canceled order was *adding* to a position
already over-limit (i.e., target was making it worse, so canceling is reducing).
This is the v1.6 de-risk-escape-hatch logic from instrument-limits, now cleanly
applied to the cancel source_type via the canonical predicate.

**Audit symmetry:**
- Drawdown for cancel: drawdown evaluates against current NAV state, which cancel
  doesn't mutate. Logically symmetric to instrument-limit: evaluate current,
  predicate gates blocking. v1.9's drawdown de-risk-escape-hatch handles this. ✓
- CB block_new_risk: predicate-gated. ✓
- result_reason: no new values for this patch.

## P4 — Sign-flip exit-breach result_reason: separate value (open Q1, lean: separate)

**Context:** When an action both (a) crosses zero (sign-flip) and (b) breaches a
limit on the post-flip side, v1.10 reused `evaluated:reducing_exit_complete`. This
conflates two distinct outcomes that operators want to distinguish in audit:

- "I exited cleanly to flat or near-flat" (intended)
- "I overshot and now have an opposite-side position over-limit" (probably
  unintended; investigate)

**Patch:** Introduce `evaluated:exit_with_flip`. Conditions:

```
flip_occurred       := (sign(Q) ≠ 0) AND (sign(Q') ≠ 0) AND (sign(Q) ≠ sign(Q'))
exit_with_flip      := flip_occurred AND limit_breached_on_Q_prime
exit_clean          := flip_occurred AND NOT limit_breached_on_Q_prime

result_reason := CASE
                   WHEN exit_with_flip   THEN 'evaluated:exit_with_flip'
                   WHEN exit_clean       THEN 'evaluated:reducing_exit_complete'
                   ...
                 END
```

Predicate semantics unchanged: `is_genuinely_risk_reducing` for sign-flip cases
already returns true when `Q_if_target_remaining_filled = 0` clause covers
through-zero (R11 formula admits this via the `OR Q_if_target_remaining_filled = 0`
disjunct). For strict overshoot (lands on opposite side, abs > 0), the predicate
returns false because `sign(Q') ≠ sign(Q)` and `Q' ≠ 0` violates the conjunction.

This means an `exit_with_flip` is **non-blocking only if** the limit is non-blocking
or `is_genuinely_risk_reducing=true` for some other reason — which in practice means
the operator chose to allow flips through configuration, not via predicate.

**Audit symmetry:**
- Drawdown: not applicable (drawdown is a portfolio/strategy aggregate, not
  per-position). No new result_reason here.
- Instrument-limits: applies. ✓
- CB block_new_risk: applies. ✓
- result_reason taxonomy: new value `evaluated:exit_with_flip`.

## P5 — CB throttle × cancel exemption (v1.11 self-discovered)

**Discovery:** v1.10 defines four CB actions (warn_only, block_new_risk, throttle,
hard_stop). R10 audited the canonical predicate against block_new_risk explicitly.
Throttle was not audited. The R10 holistic-audit principle didn't catch this
because the audit list was specified as "drawdown / instrument-limits / CB
block_new_risk / result_reason" — throttle wasn't in scope.

**Problem:** Throttle without exemption rules creates two failure modes:
1. Cancels rate-limited during a CB-active regime: operator cannot unwind risk
   precisely when unwinding is most needed. Throttling cancels is operationally
   backwards.
2. Genuinely-risk-reducing intents/orders rate-limited: same problem at lower
   severity. The predicate gates block_new_risk for risk-reducers; throttle should
   follow the same logic.

**Patch:** Throttle CB action exempts:
- All `source_type='cancel'`, **regardless of predicate value** (including
  `cancel_no_effect`, on the principle that no-op cancels are also not worth
  throttling and the runtime shouldn't have to special-case them).
- Any action where `is_genuinely_risk_reducing=true`.

```
-- Inside CB action resolution, when active CB action = 'throttle':

throttle_exempt := (source_type = 'cancel')
                   OR is_genuinely_risk_reducing

effective_cb_action := CASE
                         WHEN throttle_exempt THEN 'warn_only'
                         ELSE 'throttle'
                       END

-- result_reason addition for the throttle row:
result_reason := CASE
                   WHEN throttle_exempt AND source_type = 'cancel'
                     THEN 'cb_throttle:cancel_exempted'
                   WHEN throttle_exempt AND is_genuinely_risk_reducing
                     THEN 'cb_throttle:risk_reducer_exempted'
                   ELSE 'cb_throttle:applied'
                 END
```

**Audit symmetry:**
- block_new_risk: already exempts via predicate (v1.10 R10). Cancel-source-type
  exemption is implicit there because predicate handles cancel logic. The new
  cancel-source-type exemption in throttle is *broader* than predicate (covers
  cancel_no_effect too). This asymmetry is intentional: block_new_risk for a
  no-op cancel is harmless (nothing happens either way), but throttling a no-op
  cancel makes the runtime do extra accounting for no benefit.
- hard_stop: by definition blocks all actions including risk-reducers and cancels
  (fail-closed semantics, v1.9). No exemption.
- warn_only: no enforcement; no exemption needed.
- Drawdown / instrument-limits: throttle is a CB-level action, not a limit-type
  action. No change in those branches.
- result_reason taxonomy: 3 new values for throttle (`cb_throttle:applied`,
  `cb_throttle:cancel_exempted`, `cb_throttle:risk_reducer_exempted`).

**Reviewer decision needed:** confirm cancel-source-type throttle exemption is
broader than predicate (covers `cancel_no_effect`). If reviewer prefers strict
predicate-only (then throttling no-op cancels), patch tightens to:

```
throttle_exempt := is_genuinely_risk_reducing  -- only
```

I lean broader-exempt as drafted. Cost is a single extra disjunct; benefit is
operationally cleaner (cancels never throttled, full stop).

## P6 — Order-model assumption documentation (v1.11 self-discovered, V1-verified)

**Discovery:** R11's formula assumes the order model is `(quantity, filled_quantity)`
with no separate `canceled_quantity` field on `trading.orders`. V1 verification
confirms this assumption against `alembic head=0008`.

**Patch:** Add an explicit assumption block to the migration design doc:

```
ASSUMPTION (V1-verified against alembic 0008):
  trading.orders carries (quantity, filled_quantity) where:
    - quantity        = current outstanding order size
                        (reduced transactionally on partial cancel via the
                        process_cancel_update_order trigger)
    - filled_quantity = cumulative filled, NOT NULL DEFAULT 0,
                        constrained 0 <= filled_quantity <= quantity
    - remaining open  = quantity - filled_quantity
  No canceled_quantity column on trading.orders.

Partial-cancel audit trail:
  trading.cancels.quantity_canceled records cancel events for audit/idempotency.
  It is NOT consulted by the canonical predicate. The order's `quantity` field
  is the ground truth for remaining-at-risk computation; the trigger keeps it
  consistent transactionally with cancels insertions. A reader wondering "why
  don't we sum trading.cancels.quantity_canceled?" should know: because
  orders.quantity already reflects all committed partial-cancel reductions.

Cancel-of-cancel: structurally impossible (see V3-verified note in
open-questions section). The predicate does not need a recursion guard.
```

This is documentation-only. No SQL behavior change.

## P7 — CB hard_stop interaction with cancel_no_effect (P2 cross-reference)

**Clarification, not a new patch:** P2's `blocking=false` for `cancel_no_effect`
holds **except when CB hard_stop is active**. hard_stop is the fail-closed
escape from all predicate logic — it blocks regardless of source_type, regardless
of predicate, regardless of effect-vs-no-effect. Documented in v1.9 as intentional
fail-closed; reaffirmed here for v1.11 audit completeness.

```
-- Final blocking resolution for cancel_no_effect:
final_blocking := CASE
                    WHEN active_cb_action = 'hard_stop' THEN true
                    ELSE false
                  END
final_result_reason := CASE
                         WHEN active_cb_action = 'hard_stop'
                           THEN 'evaluated:cancel_no_effect:cb_hard_stop'
                         ELSE 'evaluated:cancel_no_effect'
                       END
```

New result_reason composite: `evaluated:cancel_no_effect:cb_hard_stop`.

(Composite reasons follow v1.10's existing pattern for CB-superseding-evaluation
verdicts.)

## Updated cancel-flow outcome matrix

| Cancel scenario | predicate | result_reason (limit branch) | blocking |
|---|---|---|---|
| Target has remaining > 0, target was reducing exposure | false | `evaluated:limit_breached` (if breached) | true |
| Target has remaining > 0, target was adding/sideways | true | `evaluated:reducing_exit` (if breached) | false |
| Target has remaining > 0, target was reducing, current Q within limit | false | `evaluated:within_limits` | false |
| Target has remaining > 0, target was adding, current Q within limit | true | `evaluated:within_limits` | false |
| Target has remaining = 0 (no-op) | false | `evaluated:cancel_no_effect` | false |
| Target has remaining = 0 (no-op), CB hard_stop active | false | `evaluated:cancel_no_effect:cb_hard_stop` | true |

This matrix is exhaustive over the cancel branch as of v1.11. It is the test
oracle for SQL-phase cancel test cases.
